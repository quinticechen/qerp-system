# Parallel Development Coordination (AI Session × RBAC Session)

> Since 2026-10-07, this project has been developed by two Claude Code sessions at the same time, sharing one working directory, the `main` branch and one Supabase database. **Both sessions read this document before making any change**, and update §5 when the handoff status changes.
>
> - **AI Session**: Query AI Agent architecture, wrapping APIs as tools, evals ([QUERY_AGENT_PHASE1.md](./requirements/QUERY_AGENT_PHASE1.md))
> - **RBAC Session**: multi-tenant roles and permissions, plus Phase 1 packaging each feature as an API and moving the frontend onto the APIs ([MULTI_TENANT_RBAC.md](./requirements/MULTI_TENANT_RBAC.md))
>
> Since 2026-10-08, Phase 1 has been split this way (user decision): the business APIs and moving the frontend onto them moved from the AI Session to the RBAC Session.

## 1. Ownership

Only change what you own; when you need to touch the other session's area, leave a request in §6 for them to handle.

| Area | AI Session | RBAC Session |
|------|------------|--------------|
| Code | `mcp-server/**`, `src/components/query/**`, `src/hooks/useQueryChat.ts`, `src/hooks/useQueryAction.ts`, `src/lib/queryApi.ts`, `scripts/verify-query-ui.py` | `src/components/{organization,user,permission}/**`, `src/hooks/useOrganization*.ts`, `src/hooks/usePermissions.ts`, `PermissionGuard`, `src/components/AppSidebar.tsx`, routes, `supabase/tests/**` |

| Documents | `docs/QUERY_AGENT_*.md` | `docs/MULTI_TENANT_RBAC.md`, business API documentation |

Business pages (the frontend components for products, orders, purchasing, inventory, shipping, etc.) are changed by the **RBAC Session**: both the R2 frontend gating and the Phase 1 move to APIs belong to that session. The AI Session changes only the Query-related frontend (table above).

Re-read any file before changing it (the other session may have just changed it).

## 3. Git

- Both sessions share one working directory and the `main` branch, **without worktrees** (a new worktree has no `node_modules`, the project rules forbid installing them, and there is only one dev server and one database)
- Commit only by explicit path: `git add <your files>`; `git add -A`, `git add .` and `git commit -a` are **forbidden**
- When a shared file holds changes from both sides, stage only your own hunks (apply a patch with only your hunks via `git apply --cached`)
- Commit in small, frequent steps; check with `git diff --cached --stat` before committing that only your files are staged
- Commit only when the user asks

## 4. Database

There is only one Supabase database, and both sessions' migrations are applied straight to production.

1. Name migrations with **the time of creation** (`YYYYMMDDHHMMSS_name.sql`) to avoid number collisions
2. Run `list_migrations` before applying, to see what the other side applied recently
3. **Never `CREATE OR REPLACE` an object the other side owns** (§1); raise a request in §6 when needed
4. Run the Supabase security advisor after applying
5. Test data: both sides share the test account `lovejoker369+test@gmail.com` (admin of lo1, owner of lo2). Don't delete test data the other side created

### Contracts (both sides depend on them; changes need agreement from both)

| Contract | Content |
|----------|---------|
| Permission check | The single check function is `user_has_organization_permission(auth.uid(), organization_id, '<key>')`; RPCs, RLS and the AI's `authGuard` all use it |
| Permission keys | The permission catalog is maintained by the RBAC Session (`permission_definitions`). The `permission` declared by AI tools and the `PermissionKey` in `mcp-server/src/tools/types.ts` must be keys from the catalog; when keys are added to or removed from the catalog, notify the AI Session in §6 |
| Business APIs (RPCs) | Written by the RBAC Session. Each starts by checking, with the function above, the permission key for **the task itself**, and confirms that referenced data belongs to the same organization; an AI tool's `permission` equals the key that RPC checks |
| API → Tool | Each API group, on delivery, must meet [QUERY_AGENT_PHASE1.md](./requirements/QUERY_AGENT_PHASE1.md) §2: parameter descriptions, read/write, permission key, organization scope, **dry-run mode `p_dry_run` on write RPCs** (validates and returns the content expressed with names, without writing), error codes + Chinese messages, display numbers in the return value, deactivate instead of delete |
| Business table RLS | Written by the RBAC Session. **Tighten a table's RLS only after its RPCs are live (marked "RPC done" in §5)**, otherwise cross-domain triggers break (MULTI_TENANT_RBAC.md P7) |
| Permission matrix tests | Maintained by the RBAC Session, covering the APIs it writes |
